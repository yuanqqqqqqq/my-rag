# my-rag

> **把手边的文档变成一个能问答的知识库。**
>
> 一条命令建索引，一条命令提问。支持 Markdown / PDF / Word / 纯文本 / 代码，
> 中英文自动识别。

不是 LangChain 的封装 —— 切块、检索、融合、精排全部自己实现。
每个默认参数都有依据，不是调参试出来的。

## 快速开始

需要 **Python 3.10+** 和一个智谱 API Key（[open.bigmodel.cn](https://open.bigmodel.cn/)，`glm-4-flash` 免费）。

```bash
# 1. 安装。-e 会顺带注册 my-rag 命令
pip install -e .

# 2. 配 Key
cp .env.example .env        # 填入 ZHIPUAI_API_KEY

# 3. 用一个内置的中文示例语料试试（公司制度文档）
my-rag index examples/hr-demo --name hr-demo --exclude "*.txt"

# 4. 提问（--show-hits 顺带打印材料来源）
my-rag ask "怎么申请年假？需要什么材料" -i hr-demo --show-hits
```

```
检索到的材料：
  [1] 年假制度.md  llm=8
  [2] 病假规定.md  llm=5
  ...

申请年假需要按照以下步骤操作：

1. 员工需在 OA 系统提交年假申请单。
2. 提交申请单后，需经直属上级审批后生效。

所需材料：无特别要求的材料，只需在 OA 系统中提交申请单即可。

[耗时] 检索 2.80s + 生成 4.14s
```

不想装包也行：`pip install -r requirements.txt`（钉死了实测通过的版本组合），
然后在仓库根目录把上面的 `my-rag` 换成 `python -m rag`。

### 用你自己的文档

```bash
my-rag index ~/Documents/我的笔记 --name notes
my-rag ask "之前记的那个部署流程是什么" -i notes
```

## 支持什么

| 格式 | 切块策略 | 说明 |
|---|---|---|
| `.md` `.markdown` | 按标题层级切 | 每块知道自己属于哪一节 |
| `.txt` `.rst` `.log` `.csv` | 按段落递归切 | 无结构信息，按长度兜底 |
| `.pdf` | 按页提取后递归切 | 标注页码，方便溯源 |
| `.docx` | 段落 + 表格 | 表格单独提取（关键信息常在表里） |
| `.py` `.js` `.go` `.java` … | **按函数/类边界切** | 别把函数劈成两半 |

**自动跳过**：`.git` / `node_modules` / `__pycache__` 等目录，以及超过 2M 的文件。
**可手动排除**：`--exclude "*.txt" "draft_*"`

**中文支持**：自动识别语料语言，中文走 jieba 分词（BM25 对中文必需）。
领域词不认识？喂一个词典：`--dict domain.txt`（见下方「中文语料」）。

## 检索策略

```
                BM25 加不加？    LLM 精排加不加？
vector              ✗                ✗           基线，最快
hybrid              ✓                ✗           加了关键词召回
rerank              ✗                ✓           默认，最稳
hybrid-rerank       ✓                ✓           全都要
```

```bash
my-rag ask "问题" --strategy vector      # 换策略
```

**为什么默认是 `rerank`？** 因为它用 cross-encoder，
而向量检索是 bi-encoder —— 前者能判断「这段答没答」，后者只能判断「像不像」：

```
bi-encoder    ：[问题] ──▶ 向量A ┓
                                  ├─ 比距离      ← 只能比"像不像"
                [文档] ──▶ 向量B ┛

cross-encoder ：[问题 + 文档] ──▶ 一个模型 ──▶ 分数   ← 能读懂"答没答"
```

代价是每次查询多 8 次 LLM 调用（8 个候选各打一次分，**已并发，约 1.2 秒**）。

> **瓶颈已经转移到生成那一步了** —— 上下文长、答案也长时，生成要 5~15 秒。
> 这时候开流式：`my-rag ask "..." --stream`，首字延迟能压到 1 秒内。

**取舍见下方的「局限」。**

## 中文语料

中文和英文的检索链路不一样，有两点要注意：

| 问题 | 现象 | 解法 |
|---|---|---|
| **jieba 不认识领域词** | `年假` 被切成 `年`/`假`、`报销单` 切成 `报销`/`单` | 自定义词典 `--dict` |
| **BM25 分不清复合词** | 文档写`申请单`、你搜`申请`，对不上 —— 问年假却返回病假 | `rerank` 策略（cross-encoder 读内容，不受词形影响） |

> 分词默认**保留全部 token（含单字）**，不做过停用词过滤 ——
> 一是兜底 jieba 切碎领域词的情况，二是 BM25 的 IDF 本来就会降权高频词。

**建索引时会自动检查有没有词被切碎，并提示你补词典：**

```
提示：以下词可能被分词器切碎了
    年假     (出现 5 次)
  中文没有空格，分词错了不会报错，只会让检索悄悄变差。
  如果它们在你的领域里是一个词，加进词典再重建：
    my-rag index <路径> --dict domain.txt
```

> 为什么要主动提示：中文分词错了**不会报错**，只会让检索效果悄悄变差。
> 遇到这种情况，人会去怀疑 embedding、怀疑切块、怀疑模型，
> 唯独想不到是分词的锅 —— 所以这类问题必须由工具自己暴露出来。

```bash
# 领域词词典格式：每行一个词，可选跟词频和词性
# 年假 100 n
# 带薪年休假 50 n
my-rag index ./docs --dict domain.txt
my-rag ask "..." --dict domain.txt      # ⚠️ 建索引和查询必须用同一份
```

内置的中文示例语料 `examples/hr-demo/` 自带一份 `dict.txt`，可以照着改。

或者设置一次环境变量，两边自动生效：

```bash
export MY_RAG_DICT=domain.txt
```

## 命令

```bash
# 索引与配置
my-rag init [路径]                          # 生成 .ragignore 和 rag.toml 模板
my-rag index <路径...> --name NAME          # 建索引（可给多个路径）
my-rag index ./docs --dry-run               # 预演：看会索引什么，不花 API
my-rag index ./docs --dict domain.txt       # 带自定义分词词典
my-rag index ./docs --exclude "*.tmp"       # 排除文件
my-rag index ./docs --rebuild               # 全量重建（默认是增量）
my-rag index ./docs --docs-src data/docs_src  # 展开 Markdown 里的代码引用指令
my-rag list                                 # 列出所有索引
my-rag info -i NAME                         # 索引详情
my-rag drop NAME                            # 删除索引

# 问答
my-rag ask "问题" -i NAME                   # 提问
my-rag ask "问题" --brief                   # 简洁模式（快约 6 倍，见下）
my-rag ask "问题" --stream                  # 流式输出（首字 0.3s vs 2.6s）
my-rag ask "问题" --show-hits               # 同时打印材料来源
my-rag ask "问题" --top-k 8                 # 喂给生成器的块数（默认 4）
my-rag ask "问题" --strategy vector         # 换检索策略
my-rag ask "问题" --json                    # 结构化输出，便于管道集成
my-rag ask -f questions.txt --json          # 批量问答，输出 JSONL
my-rag retrieve "问题" --json               # 只看检索，不生成（便宜，适合调检索）

# 多轮对话（追问能引用前文）
my-rag chat -i NAME                         # "怎么申请年假？" → "那病假呢？"
my-rag chat -i NAME --no-rewrite            # 关掉追问改写（做对照用）

# 排查（这个最有用）
my-rag trace "问题"                         # 逐层打印检索管线
my-rag trace "问题" --answer                # 顺带生成答案

# 服务与评估
my-rag serve                                # HTTP API + 网页界面（需 pip install -e '.[serve]'）
my-rag eval --strategies vector rerank      # 对比多个检索策略
my-rag eval --runs 3                        # 重复 3 轮，测稳定性
my-rag eval --eval-set my.json              # 换一份自定义评估集
```

`ask` / `chat` / `retrieve` / `trace` 都接受 `-i/--index` 和
`--strategy vector|hybrid|rerank|hybrid-rerank`；`eval` 用复数形式
`--strategies`，一次给多个做对比。

## 用法详解

### 增量索引：改一个字，不重算全库

索引里每个块的 id 是**内容哈希**，所以"哪些块变了"是个集合差运算：

```bash
$ my-rag index ./notes --name notes
增量更新完成：新增 0，复用 534，删除 0 —— 现共 534 块    # 内容没变，0 次 API 调用

$ echo "新增一句话" >> notes/one.md
$ my-rag index ./notes --name notes
增量更新完成：新增 1，复用 533，删除 1 —— 现共 534 块    # 只有变化的那块重算
```

**不做这个，工具就没法日常用** —— 每次编辑都要付一次全量 embedding 费用。

### 项目配置：让参数跟着索引走

```bash
my-rag init ./my-docs      # 生成 .ragignore 和 rag.toml 模板
my-rag index ./my-docs     # 零参数，自动读配置
```

```toml
# rag.toml
name = "my-docs"
dict = "domain.txt"        # 中文领域词词典
exclude = ["*.min.js"]
```

**建索引时的参数会被写进索引本身**，`ask` 时自动读回来。

这修掉了一个真实的坑：分词词典必须**建索引和查询时一致**，
否则查询和文档的切法对不上，**BM25 会静默失效** —— 不报错，只是效果悄悄变差。
靠用户每次记得加 `--dict` 是靠不住的。用 `my-rag info` 可以查看某个索引记录的参数。

### 多轮对话：改写追问，但不让模型生成内容

追问本身不足以检索 —— "那它怎么配置？"里，"它"是什么，检索系统看不见。
所以每轮先把追问改写成独立问题：

```
你 > 怎么申请年假？
助手 > ...
  来源: 年假制度.md, 病假规定.md

你 > 那病假呢？
助手 > ...
  改写为「怎么申请病假？」        ← 补全指代，检索才找得到
  来源: 病假规定.md, ...

你 > 这两种假有什么区别？
助手 > （正确综合了两份文档回答）
  改写为「年假和病假有什么区别？」  ← 从对话历史里解析出"这两种假"
```

**改写只做「补全指代」，不做「重写问题」。** 它把"它 / 这个 / 这两种"换成具体所指，
**不引入用户没提过的术语** —— 因为让模型自由发挥时，它会用自己的旧知识往里塞词，
那些词可能根本不在你的语料里，反而把检索带偏。

改写结果会实时显示出来，方便你核对。如果模型真编了语料外的词，会自动回退到原问题。
想关掉这道护栏做对照：`--no-rewrite-guard`；连同术语校验一起关：`--no-check-oov`。

### `--brief`：快 6 倍，但有代价

**生成耗时完全由输出长度决定**，不是上下文长度。同一份上下文：
答案 294 字要 4.2 秒，1217 字要 20.8 秒。而模型的默认风格很啰嗦 ——
一个"怎么上传文件"能写 1790 字。

`--brief` 加一句长度约束，实测：

| | 耗时 | 关键词命中 | 答案相关性 |
|---|---|---|---|
| 默认 | 17.4s | 86% | 9.4 |
| `--brief` | **3.0s** | 86% | 9.1 |

**但指标测不出它的代价** —— 对"怎么用 X"这类问题一句短答案够用，
对需要列举/比较的问题，短答案会把结构丢掉：

```
默认（11.3s）                      --brief（6.1s）
年假和病假的区别：                  年假和病假的区别在于：年假是员工享有的
1. 申请条件：...                    带薪休假，按工龄递增天数；病假是因员工
2. 申请流程：...                    生病无法出勤，需提供医疗证明，期间工资
3. 休假天数：...                    打折。
4. 工资待遇：...
5. 是否需要医疗证明：...
6. 是否需要请假单：...
```

**所以这不是能优化掉的性能问题，是速度与完整度的取舍。**
默认给完整的，急着要答案就加 `--brief`。

> 顺带说：这也说明**纯指标驱动的优化有盲区** ——
> 关键词和相关性两项都测不出"结构丢了"这件事。

### 流式输出的实际收益

```
非流式：总 2.65s   首字 = 2.65s（一直盯着空屏幕）
流式  ：总 1.89s   首字 0.32s   ← 首字延迟缩短 88%
```

**总时长差不多，但感知完全不同。** 只用在生成那一步 ——
精排必须拿到全部分数才能排序，没法流式。

### `trace` 长什么样

调检索时最有用的一个命令 —— **一次就能看出是「召不到」还是「排错了」**：

```
【1】向量召回 top-20   bi-encoder：问题和文档分别编码，比余弦距离
    1. [0.8731] 年假制度.md
    2. [0.9410] 病假规定.md
    ...
【2】BM25 关键词召回 top-20   sparse：词频分，看得见字面看不见语义
    1. [    1.33] 病假规定.md          ← 它反了
    2. [    0.23] 远程办公.md
    3. [    0.14] 年假制度.md
【3】RRF 融合 top-8            ← 融合后错误的一路赢了
    1. [0.03252] 病假规定.md
    2. [0.03227] 年假制度.md
【4】LLM 精排：逐条打分         ← cross-encoder 把它掰回来
    llm=   6   病假规定.md
    llm=   8   年假制度.md
【5】最终喂给生成器的 top-4
   [1] 年假制度.md                ← 正确
```

## HTTP 服务

```bash
my-rag serve --port 8000     # 打开 http://127.0.0.1:8000 就是网页界面
```

```
GET  /            最小网页界面
GET  /health      健康检查
GET  /indexes     列出所有索引
POST /ask         {"question": "...", "index": "...", "strategy": "..."}
POST /retrieve    同样但不生成答案（便宜）
```

> ⚠️ 这是**本地工具的服务端**：没有鉴权、没有限流、默认只监听 127.0.0.1。
> 别直接挂公网 —— 它背后的 LLM API 是按量计费的。

## 评估

```bash
python scripts/fetch_data.py                 # 评估集针对 FastAPI 语料，先拉语料
my-rag index data/fastapi-repo/docs/en/docs/tutorial --docs-src data/docs_src --name fastapi_docs
my-rag eval --strategies vector rerank --runs 3
```

评估集 `evaluation/eval_set.json` 有 9 道题，分两个队列：

| 队列 | 题数 | 内容 |
|---|---|---|
| A | 7 | 语料里**有**答案，来源文件已逐条核对 |
| B | 2 | 语料里**没有**答案（如"法国的首都是哪"），测会不会硬编 |

**两个队列必须分开看。** 把"库里没有"的题和"有答案"的题混在一起平均，
检索相关性会被整个拉下来，诊断从「良好」变成「改检索」——
让人去修一个不存在的问题。B 队列看的是另一件事：**老实拒答**。

指标分两类：

| 类型 | 指标 | 怎么读 |
|---|---|---|
| 确定性 | 命中@K、命中名次、关键词命中率、老实拒答 | 无随机性，改动的第一判据 |
| LLM 裁判 | 检索相关性、忠实度、答案相关性 | 0-10 分，同一份答案重评会差 ±1 |

名次另有一个**含惩罚**口径：未命中按 `top-k + 1` 计入平均名次。
只看"平均名次"会被幸存者偏差骗到 —— 少命中一题的方案反而显得更好。

跑完末尾给一句诊断：

```
检索相关性低→改检索 ； 忠实度低→改生成防幻觉 ； 答案相关性低→改生成/query改写
```

**改进幅度小于 1 分不可信** —— LLM 裁判的噪声就在这个量级。
要换评估集，复制 `eval_set.json` 改，然后 `--eval-set my.json`。

## 环境变量

| 变量 | 作用 |
|---|---|
| `ZHIPUAI_API_KEY` | **必填**。智谱开放平台的 Key，写进 `.env` 或直接导出 |
| `RAG_CHAT_MODEL` | 覆盖默认对话模型（默认 `glm-4-flash`） |
| `RAG_RERANK_WORKERS` | 精排打分并发度，默认 8；设成 1 就是串行 |
| `MY_RAG_DICT` | 全局分词词典路径，建索引和查询两边都生效 |

其余可调参数（`CHUNK_SIZE` / `RECALL_K` / `FINAL_K` / `RERANK_POOL_K` 等）
都收在 `rag/config.py`，单点可改。

## 设计取舍

| 决策 | 为什么 | 代价 |
|---|---|---|
| **精排逐条打分**，不一次排 8 个 | 一次排序容易漏项/重项，解析失败就得静默降级 | 每次查询多 8 次 API 调用（已并发，约 1.2s） |
| **追问改写只补全指代**，不让模型重写问题 | 模型自由发挥时会引入语料里不存在的词 | 放弃了一部分改写收益 |
| **块 id 用内容指纹**，不用序号 | "这块变了没"退化成集合差运算，不用维护 id 对照表；指纹里带上 `source`，两篇文档里的相同段落不会被并成一个 | 改一个字就是一个新 id；块序号是语料级的，不对应文档内位置 |
| **检索质量下降时先 `trace`，不要先改代码** | 检索层能看到中间结果，生成层是黑盒 | 需要用户理解五层输出 |
| **不用停用词表** | BM25 的 IDF 本来就会降权高频词，手工过滤是重复劳动还容易误伤 | 索引略大 |
| **保留单字 token** | 兜底 jieba 切碎领域词的情况 | 索引略大 |
| **`--brief` 默认关** | 指标上和完整版打平，但它会把需要列举/比较的答案压成一句话 | 默认多花十几秒 |
| **工具自身的配置文件永不索引** | `rag.toml` / `.ragignore` 是工具的东西，不是语料 | 用户目录里同名文件不会被索引 |

## 局限

诚实地列出来。**知道自己工具的边界在哪，比多写一个亮点更重要。**

1. **rerank 在候选同质时不可靠**：已定位原因（粗粒度打分 + 平局），未根治。
   可能的方向是成对比较（pairwise）而非绝对打分。
2. **评估集只有 9 题**（7 题有效），且忠实度/答案相关性接近满分 ——
   **存在质量天花板，测不出检索优化的收益**。要验证收益需要更难的题。
3. **LLM 裁判本身会飘**：实测 9 题里 3 题两次运行差 ±1。
   **改进幅度 < 1 分不可信**，确定性指标更值钱。
4. **rerank 的延迟成本真实**：端到端约 6 秒（8 次额外调用）。
   如果生成器会读完整上下文，这个收益可能不划算。
5. **PDF 提取质量不稳定**：取决于 PDF 本身，扫描件完全无效（没有 OCR）。
6. **未解决问题**：某道评估题的关键词命中率一直是 0%，未查明。

## 常见问题

**`my-rag: command not found`**
没装成命令。`pip install -e .`，或者用 `python -m rag` 代替。

**报错 `1210 API 调用参数有误`**
智谱 embedding 的硬限制撞上了：单条 ≤ ~3072 tokens，单次请求 ≤ 64 条。
**报错信息完全不提"太长"**，所以遇到这个先往长度上查。
批大小在 `rag/config.py` 的 `EMBED_BATCH_SIZE`。

**中文检索效果不对**
多半是分词。建索引时如果检测到领域词被切碎会打提示，按提示加词典重建：

```bash
my-rag index ./docs --dict domain.txt --rebuild
```

**改了文件但索引没更新**
先 `my-rag index ./docs --dry-run` 看它到底扫到了什么。
`.git` / `node_modules` / 超过 2M 的文件会被自动跳过，`.ragignore` 里的规则也会生效。

**忘了索引叫什么名字**
`my-rag list`。
